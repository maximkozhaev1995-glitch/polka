## Изменения

- `public.apply_stock(uuid,jsonb)` — SECURITY INVOKER оболочка над закрытой SECURITY DEFINER реализацией с пустым search_path. Только authenticated получает EXECUTE; anon/PUBLIC отозваны. Пользователь определяется по подписанному числовому `sub` Telegram JWT; UUID `auth.uid()` здесь неприменим.
- Заведение, роль и права читаются из `users`, строка сотрудника блокируется FOR SHARE на время операции. Клиентские actor/venue/left/prev/at не используются. Автор, время, предыдущие значения и полное состояние после движения (next_state) формируются сервером.
- Пакет 1–200 уникальных позиций, одна транзакция. Блокировки в порядке id, включая ещё не созданные остатки; контроль revision, целых неотрицательных остатков (до 1 000 000). Ошибка любой строки или вставки движения откатывает весь пакет и квитанцию запроса.
- Ключ идемпотентности уникален в заведении, связан с автором и полным JSON запроса. Идентичный повтор возвращает прежний ответ. Другой payload/автор с тем же ключом отклоняется. Квитанции не удаляются автоматически.
- Раздельные права мастера: add увеличивает остатки; take уменьшает только при переносе/замене банки на стойке; offbar снимает со стойки; slow/unstop управляют соответствующими метками. Списание, инвентаризация, вывод позиции и отмена — управляющему. Автоматический стоп нельзя подделать для обхода unstop.
- Прямые INSERT/UPDATE/DELETE/TRUNCATE stock/moves закрыты для клиентов, включая отдельные привилегии на колонки. Старый неточный `stock_master_guard` заменён проверками RPC. Существующие SELECT/RLS сохраняются.
- Подтверждение черновика, быстрые операции, инвентаризация, метки и начальный остаток нового вкуса используют RPC. Прямые клиентские записи движений запрещены также в адаптере. Отрицательное количество не обрезается до нуля.
- Отмена добавляет обратное движение и разрешена только для последней версии позиции. История не удаляется. Старые движения без operation_id автоматически не отменяются; менеджер может сделать проверенную корректировку.
- Перед отправкой запрос и UUID сохраняются в localStorage с привязкой к заведению и сотруднику. После неизвестного результата другой запрос блокируется; кнопка «Восстановить результат складской операции» повторяет исходный запрос. Подтверждённый черновик хранит исходные версии/значения для повтора после перезагрузки. Сопоставленные строки черновика удаляются только после успешного результата.

## Неразрешённые риски — блокируют production

1. В репозитории нет базовой DDL stock/moves/users/flavors. SQL проверен на явно описанной тестовой схеме, не на копии настоящей базы. Нужны сверка типов, ограничений, индексов, триггеров, ACL и RLS, в том числе безопасности изменения users/perms, существующих RPC и представлений. Любой старый SECURITY DEFINER RPC либо доверенный service_role может обходить отозванные клиентские права; инвентаризация таких путей обязательна.
2. PGlite использует одну сессию. Проверка конкурирующих запросов доказывает защиту revision при последовательном исполнении, но не реальную конкуренцию сессий. На отдельном PostgreSQL/Supabase нужны одновременные одинаковые UUID, разные UUID на последнюю единицу, пересекающиеся пакеты в разном порядке, создание отсутствующей строки, отзыв прав, ожидание/таймауты блокировок и rollback при обрыве соединения.
3. Миграция создана CLI в `supabase/migrations/`; старые `migrations_001…021.sql` лежат вне этого каталога и полной базы не создают. **Не запускать db push/reset на рабочем проекте.** Нужно согласовать baseline и порядок миграций. Отрицательные исторические остатки остановят CHECK и откатят миграцию; их исправление требует отдельного решения, автоматически данные не чистятся.
4. Не выполнен браузерный/Telegram/PostgREST прогон на отдельном стенде: UI восстановления, две вкладки, поведение при недоступном localStorage, refresh JWT, реальные ответы API и видимость журнала. LocalStorage не заменяет серверную квитанцию: после ручной очистки/повреждения хранения неизвестный исход нужно выяснять по журналу, а не создавать новый запрос. Одновременные вкладки не имеют общей клиентской блокировки; stale revision не позволит повторно списать одну версию, но UI восстановления надо проверить.
5. Создание каталожного вкуса и начальный остаток остаются отдельными транзакциями: возможен вкус без остатка, но невозможно изменение остатка без движения. Сводный inv_log инвентаризации и заказ также отдельны от stock/moves; сбой сводки не откатывает склад. Автодозаказ после успешного подтверждения склада по-прежнему сохраняется отдельно и не входит в транзакцию RPC. Пакеты >200 отклоняются целиком и требуют разделения человеком.
6. Нулевые изменения/метки пишут движения kind=in с qty=0; отмена — kind=in с reason, поэтому внешние отчёты должны учитывать reason/qty, а не только kind. Квитанциям и журналу нужны согласованные сроки хранения без нарушения защиты повторов. Старые клиенты после миграции потеряют возможность писать напрямую: нужны согласованный выпуск клиента/миграции и план отката без удаления аудита.
7. Проверки Supabase advisors и настоящая интеграция не запускались: разрешения на подключение к тестовому проекту не предоставлялись. Claude/OCR/платные API не вызывались и не нужны для B5.

## Какие разрешения нужны дальше

- Отдельное разрешение и реквизиты **изолированного тестового проекта**, либо локального PostgreSQL с несколькими сессиями, с обезличенной схемой/данными и правом применять только тестовые миграции. Секреты передавать через защищённое окружение, не через PR/чат.
- Разрешение на браузерный/Telegram прогон против такого стенда и запуск advisors только на нём.
- Production-миграция, изменение секретов/Edge Functions, merge и deploy требуют отдельного явного разрешения после закрытия рисков. В текущую работу они не входят и не выполнялись.

При проектировании сверены официальные разделы Supabase Database functions и Changelog: https://supabase.com/docs/guides/database/functions и https://supabase.com/changelog .
